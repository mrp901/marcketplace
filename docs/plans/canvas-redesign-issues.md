# Plan: file the canvas-redesign GitHub issues on mrp901/marcketplace

## Context
Reviewing the skill-flow chart (`docs/skill-flow.md`) showed that the shared canvas drops most of what the user does on it:
- Ticks in five "acknowledge" sections only close the line.
- Idea decisions and wireframe reactions are never recorded. The taste log always says `reaction: unknown`.
- Edits and added lines are only read in two sections.
- Slack replies and @-mentions are never swept.
- An idea moving back from a parked roadmap slot goes unnoticed.
- The same news goes out three times: webhooks, canvas and briefing.

The user wants these fixed. They also want loose token-spend guidelines that don't make the skills worse.

**This document only plans issues.** A Claude instance runs this plan and files the issues described below on GitHub. Implementation happens later, from the issues themselves.

## Hard rules for the instance that files the issues
1. **Only file on `mrp901/marcketplace`.** Check `owner=mrp901`, `repo=marcketplace` on every create call.
   - Never create issues, comments or anything else on any other repo.
   - This especially covers any Bluewater repo (for example anything under `pizzi-bluewater`, or `Bw.Connect.All`).
   - If a tool defaults to, or suggests, another repo, stop.
2. Search open issues first (`search_issues` on `repo:mrp901/marcketplace`), so issues aren't duplicated if the plan is re-run.
3. Issue text must contain no organisation IDs, webhook URLs, Slack/Confluence IDs, real ticket keys or people's names. Use `PRJ-164` as the example idea key, and "the user" for the person. Implementers will copy issue text into `plugins/`, where `scrub_check.py` fails on those literals and on em dashes.
4. Write in Australian English, plainly:
   - no em-dash asides
   - no "not X, but Y" framing
   - no filler ("worth noting", "robust", "seamless")
   - short direct sentences
5. End every issue body with the footer:
   ```

   ---
   _Generated by [Claude Code](https://claude.ai/code)_
   ```
6. Labels: apply `enhancement` only if it already exists in the repo. Don't create labels.
7. File the tracking issue first. File the rest in the order below, then attach each one to the tracking issue as a sub-issue (`sub_issue_write`), and tick it in the tracking issue's checklist, with numbers filled in.
8. Report back the list of issue numbers and URLs. Don't open PRs or branches.

### 0. Tracking: "Canvas redesign: every tick means yes, do it"
- **Why:** the summary from Context above.
- **The design in one place:**
  - **Tick rules:**

    | Action | Meaning |
    |---|---|
    | Tick | Yes, do this |
    | Edit then tick | Do it my way |
    | Edit without ticking | Nothing happens yet, and the wording is kept |
    | Delete | No; suppress it |
    | Add a line anywhere | A new request |

    To-do is the one exception: it's the user's own list, and a tick there means done.
  - **Choices:** a plain question line with one checkbox per option under it. Tick one to choose it; the others close as "not chosen". Ticking two gets a `blocked · pick one` sub-line. An edited option is a variation of that option.
  - **One flow:** the Router acts on every tick, and the Briefing only closes lines and reports.
  - **Ownership:** a skill owns lines by tag prefix, not whole sections.
  - **Five sections:** Today, To-do, For you, Ideas, Closed.
  - **FYI:** goes only in the briefing message. The canvas holds only things that need the user.
  - **Nothing ever sends a message on the user's behalf.**
- **Constraints:**
  - No new schedules and no event-driven runs. The midnight Router stays.
  - skill-eval stays manual.
  - idea-deep-dive gets no selector yet.
  - Flagged email is out of scope.
- **Rollout warning:** the live scheduled routines run whatever is on `main`. Every child PR targets a long-lived branch `canvas-redesign`, and that branch is merged to `main` once, when all children are done. The first Briefing run after that merge migrates the canvas.
- **Checklist:** one line per child issue.

### 2. "Token-spend guidelines that don't degrade the skills"
- **Changes:** add a short `shared/token-discipline.md`, and link it from each `SKILL.md`'s Needs or Budget section. It sets guidelines, not hard caps:
  1. **Quiet exit first.** Each skill starts with its cheapest "anything to do?" check and stops with `runs.status = quiet` when there's nothing. For example:
     - Router: no new reactions or saves since the cursor, and no surface line differs from `state.items`.
     - Scout: no qualifying or requeued idea.
     - Wireframe: none eligible or requeued.
     - kb-dream: nothing new in the Inbox or log since the last dream, and not a monthly run.
     - Health check: no runs since the last check.
     - action-sweep: every search returns nothing new.

     Each skill writes its own condition into its `SKILL.md`.
  2. **Fast-fail early.** Precondition checks (profile keys, state readable, the identity-critical connector) come before any expensive read. This extends `onboarding.md`'s existing fast-fail rule.
  3. **One job per run.** A skill does its one job and stops. It doesn't pick up neighbouring work "while it's here"; that belongs on the For you list for a later run.
  4. **Subagents for bulk raw reading.** Reading threads, transcripts, web pages or vault search results goes to a `search`-tier subagent that returns a short structured answer, so raw content stays out of the skill's own context. This follows `model-tiers.md`. Don't use a subagent for a single small read, because the overhead outweighs the saving.
  5. **Load references lazily.** Open a `references/` file only in the step that needs it.
  6. **Read once, write once.** Keep the existing one surface read, one surface write batch and one state write per run. Use cursors so nothing is re-read.
  7. **Never trade away quality steps.** Critic audits, voice registers, verification and source citations are never skipped to save tokens. If a budget runs out, return `partial` and say what's left, rather than doing a thinner job.
- **Acceptance criteria:**
  - Every scheduled skill documents its quiet-exit condition.
  - No quality step is removed.
  - `line_budget.py` passes (move detail to `references/` where needed).
- **Depends on:** #1, for the `runs` fields.
